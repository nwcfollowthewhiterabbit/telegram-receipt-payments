# Файлы и подтверждённая оплата в CRM

## Требование и область

11.11.2026 пользователь поручил проверить штатную деталь «Файлы» и
проведение операции в существующей Terrasoft, прикреплять исходный счёт и
банковскую квитанцию, проводить созданную ботом операцию после подтверждения
оплаты банком. Для monobank отдельно согласовано: проводить по подтверждённой
оплате и прикладывать данные банковской выписки; PDF-квитанция добавляется
бухгалтером вручную через CRM. Официальный corporate API не выдаёт такой PDF.

Это новый процесс для обработок после включения новой версии. Исторические
записи, ранее доставленные квитанции и старые `bank_success` не используются
как доказательство оплаты и не запускают массовое перепроведение.
Подпись, отправка на исполнение и отмена банковского платежа остаются за
человеком. Банковские запросы нового monitor только читают состояние.

## Проверенный baseline

Source `2b576c98cfbd31581f5ec7401d409ca091321b84`; 74 tests, architecture и
outbox checks PASS. До обновления на рабочем сервере был установлен execution
`0ed9f2b…`, CRM target `Terrasoft`, запись включена; PostgreSQL healthy.

Read-only проверка схемы и native metadata `dbo.tbl_Service.XMLData`:

- Исходные bytes хранятся в `tbl_Files.FileData`, имя в `Link`, размер в
  `FileSize`, первая `Revision=1`; тип файла задаёт `enm_FileTypes`.
- `tbl_FileInCashflow` связывает `FileID` с `CashflowID`.
- `scr_FilesDetailGridArea` после добавления наследует отсутствующие права
  файла от родительской операции (`isq_GiveRightsByParentItem`).
- `ds_CashflowScript` при проведении расхода меняет статус на «Выполнена»,
  знак сумм на отрицательный, фактическую дату и права редактирования.
  Связанные договоры/резервы имеют дополнительные пересчёты. SQL-триггер
  сам по себе этих клиентских действий не выполняет.
- У SQL-login бота нет AdminUnit; owner ACL автоматически INSERT-триггером
  не создаётся. Новый процесс явно обеспечивает владельцу права на новую
  операцию и наследование прав вложениями, без общего доступа всем.

## Сценарий и инварианты

```text
авторизованный пользователь + проверенный счёт → неподписанная банковская
чернетка → локальная долговременная CRM-задача → одна операция + оригинал →
проверка банковского исполнения → связанное подтверждение + проведение той
же операции → аудит; при расхождении ручная проверка без нового платежа
```

1. Момент создания локальной задачи связан с сохранением банковского
   черновика одной транзакцией. Задача содержит постоянный UUID CRM-операции
   и конкретную базу; повторы после сбоя не генерируют второй UUID.
2. Проверка actual database сохраняется перед каждой внешней транзакцией.
   Другая база, чужой UUID или конфликт маркера отклоняются.
3. Оригинал и подтверждение имеют устойчивые ключи и SHA256. Повтор не
   создаёт вложений-дублей, не заменяет изменённый вручную файл. Исходный
   файл читается только внутри хранилища бота, с ограничением размера.
4. Приват24: проведённая исходящая выписка, точный `DLR=payment_pack_ref`,
   номер документа и полное совпадение реквизитов, суммы и валюты; ровно один
   кандидат. Квитанция получена для его `REF/REFN`. Учитывается пагинация.
5. Monobank: точные ID/externalReference, исходный счёт, контрагент, сумма,
   валюта; `DONE`, расход и отсутствие reverse. `IN_STATEMENT` и `PENDING`
   не доказывают оплату. Прикладывается банковский JSON с явным названием
   «данные выписки», а не самостоятельно изготовленная PDF-квитанция.
6. Банковское подтверждение закрепляется уникально за одной локальной
   задачей. Создание операции, получение подтверждения, проведение и
   Telegram-доставка имеют независимые состояния и повторяются безопасно.
7. Проведение проверяет исходный статус, принадлежность, сумму и значимые
   реквизиты; ручные изменения не затираются. Уже проведённая операция не
   перепроводится. Неизвестные/отменённые состояния требуют проверки.
8. Фактическая дата берётся из подтверждённого исполнения банка в часовом
   поясе Europe/Kyiv, а не из даты счёта или времени опроса. PeriodID при
   проведении сохраняется, как в штатном действии.
9. Ошибка CRM не создаёт повторного банковского платежа. Повтор внешней
   записи использует сохранённую задачу. Ошибка видна в статусе обработки.

## Проверка и эксплуатация

До persistent rollout: exact source commit/push/CI; свежий backup локальной
БД и файлов бота с изолированным restore, а также отдельный COPY_ONLY backup
рабочей CRM с CHECKSUM и восстановлением в новую изолированную базу.
Существующие рабочая/тестовая базы не перезаписываются; testd не используется.

На изолированной восстановленной CRM проверяются точные bytes и связи
вложений, наследование прав, положительное проведение и native side effects,
отказы/повторы/параллельные вызовы. Synthetic данные не создают платежей в
банках. На рабочем сервере проверяются exact image, target, migrations,
polling, health и отсутствие неконтролируемого исторического replay.

Rollback возвращает прежний image/config, сохраняя новую локальную таблицу
задач и созданные CRM-записи. Восстановление backup поверх новых операций
не является штатным откатом приложения.

## Границы реализации

Одна новая задача соответствует одному сохранённому банковскому черновику.
Данные старых обработок не включаются задним числом. Повторная загрузка
счёта остаётся отдельной попыткой по существующим правилам предупреждения.
Неизвестное состояние, отмена, возврат, неоднозначная выписка, изменение
финансовых полей, отсутствующий контрагент, закрытый договор или связанный
резерв/перенос требуют ручной проверки. Повторный запрос статуса не создаёт
новой банковской операции. После успешного проведения будущие возвраты
банк→CRM автоматически не сторнируются.

Расход получает отрицательные Amount/BasicAmount и дату исполнения банка.
Нативный пересчёт открытого договора сохраняет PrePayment и Debt с учётом
строк услуги/аренды, проведённых доходов и настройки NonCashTax. PeriodID
не меняется. Права владельца определяются через Contact→AdminUnit;
исключения ограничений берутся из native metadata установленной CRM.
Существующие права файлов не расширяются; недостающие субъекты наследуются
от операции. Native MaxFileSize проверен как 25 MiB; лимит сервиса 20 MiB,
всегда применяется меньший из двух. Нет миграции схемы внешней CRM.

Сохраняется принятый ранее fixed CashAccount mapping, включая второй банк.
Справочник CashAccount не содержит IBAN; автоподмена счёта по догадке не
добавлена. Это отдельный известный вопрос бухгалтерского маппинга.

## Установка и оставшаяся приёмка

Установлено и включено 11.11.2026 в 20:27 UTC из execution
`4b9d5bbe4f4c4572730abf4c331cff932644995f`, exact-SHA
[CI 43094014777](https://github.com/nwcfollowthewhiterabbit/telegram-receipt-payments/actions/runs/43094014777).
[Release evidence](releases/2026-11-11-crm-files-posting.md) фиксирует backup,
rehearsal и deployment. Подтверждены exact image, рабочая `Terrasoft`,
включённый процесс, оба банка LIVE, polling и health; restart count 0,
исходный DB-контейнер сохранён. При smoke новых исторических задач не было,
локальный outbox был пуст.

На изолированной восстановленной CRM все шесть групп native rehearsal
прошли: исходный файл/связь/ACL/повтор, rollback частичного проведения с
файлом, отказы при неверной сумме и связанной операции, знак/дата/PeriodID/
договор/ACL, повтор проведения и файла, отказ при ручной правке суммы уже
проведённой операции. Проверены 52 dependency objects; все 13 синтетических
UUID и проверяемые связи/права/аудит отсутствовали после rollback.

Контрольный банковский платёж при установке не создавался. Приёмка
банковского пути на первой обычной оплате и открытия файлов под конкретной
ролью бухгалтера ещё ожидается; шаги приведены в
[инструкции](user-manual.uk.md#файли-та-підтвердження-оплати).
SQL-проверка ACL не заменяет проверку интерфейса. Отдельные конкурентные
SQL-сессии rollback-only rehearsal не моделирует.

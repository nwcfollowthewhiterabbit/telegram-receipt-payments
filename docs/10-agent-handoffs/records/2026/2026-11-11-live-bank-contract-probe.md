- Статус: `completed`
- Начальный commit: `e68519fc3b49007b439b5dd898ee7693e33fc426` — первый

  завершал source commit в общем checkout.
- Scope: read-only runtime/API evidence и эта записка; production source не менялся

## Цель

По явному поручению основного агента проверить форму реальных ответов обоих
банков на уже существующих черновиках перед включением нового settlement
контура. Разрешены только ограниченные GET и чтение локальной БД; запрещены
создание, подпись, отправка платежей, проведение CRM и historical replay.

## Исходное состояние

Работающий бот использовал предыдущий release. В локальной БД для каждого
банка выбран один последний существующий draft с непустым live payment ID.
У обоих отсутствует новый `creation_context` и сохранённый точный
`create_request`; это исторические записи, автоматически не включаемые в
новый процесс. У обоих сохранён исходный счёт; у Privat24 также pack reference.

Runtime target подтверждён через Compose service/image metadata. Банковские
credentials использованы только внутри процесса через существующий
`get_settings()`; env, токены, URL с credentials, ID, IBAN, суммы, назначения
и raw responses не выводились и не сохранялись.

## Изменения и причины

- Созданы два временных локальных диагностических скрипта вне Git. Они
  переданы на stdin Python процесса в существующем bot-контейнере; файлы
  source/config на сервере не редактировались.
- Эта записка сохраняет только schema/enum evidence и результаты сравнений.
  Банковские и CRM enforcement правила не изменялись.

## Проверки

Выполнено семь GET без retries/redirects, с ограниченными timeout и точными
сохранёнными банковскими ссылками. Чтение PostgreSQL выполнялось внутри
`SET TRANSACTION READ ONLY`, затем rollback.

**Monobank — три начальных GET и один уточняющий GET:**

- Payment state вернул HTTP 200, объект с `id`, `state`;
  `state=IN_STATEMENT`, `id` точно совпал с сохранённым ID.
- Point statement вернул HTTP 200 с полями `amount`, `completedTime`,
  `counterEdrpou`, `counterIban`, `counterName`, `currencyCode`, `description`,
  `externalReference`, `id`, `receiptId`, `reverse`, `status`, `time`.
  `status=DONE`, `reverse=false`.
- Выписка точного исходного счёта в окне ±1 секунда от `time` вернула HTTP 200,
  один подходящий кандидат и выборку меньше лимита. `id`, external reference,
  отрицательная целочисленная сумма, валюта, IBAN/код/имя контрагента совпали
  с локальным draft как в point lookup, так и в account-scoped записи.
- `time` и `completedTime` — положительные integer, попали в допустимый
  интервал от создания draft до текущего времени; completed не раньше time.
- `description` не совпал с сохранённым назначением. Новый строгий matcher
  должен отказать для этого исторического примера.

**Privat24 — два начальных GET и один уточняющий GET:**

- Payment get вернул HTTP 200 и ожидаемые реквизиты непосредственно на
  верхнем уровне ответа. `payment_ref` и дополнительный `id` точно совпали с
  сохранённым payment ID. Совпали document number, исходный и получающий счета,
  код/имя получателя, сумма и валюта.
- `payment_pack_ref` в payment get отсутствовал; новый matcher допускает его
  отсутствие в этом ответе, используя сохранённый pack reference. Поля
  `payment_status`, `payment_status_short` присутствовали.
- `payment_destination` не совпал с сохранённым назначением.
- Выписка точного исходного счёта за один день создания draft вернула HTTP
  200, `status=SUCCESS`, `exist_next_page=false`; кандидата с точным
  `DLR == stored pack reference` в этом ограниченном окне не было.
  История не расширялась. Это отсутствие доказательства, а не подтверждение
  отсутствия оплаты; compatibility actual paid statement ещё не установлена.

**Уточнение расхождений назначения:**

У обоих банков локальное назначение совпало с сохранённым
`receipt.payment_purpose_final`, банковское — нет. Различаются и буквенная
последовательность, и числовые токены/цифры. Равенства после нормализации
пробелов, регистра и пунктуации нет; prefix/suffix/truncation также не
объясняют расхождение. Поэтому это не простая нормализация форматирования.
Из-за отсутствия exact create request в исторических записях нельзя доказать,
произошло ли ручное редактирование или иное преобразование на стороне банка.
Оснований ослаблять сравнение назначения не получено.

## Runtime, backup и rollback

Runtime не изменялся: сервис не перезапускался, source/config не изменялись,
PostgreSQL и CRM не записывались. Bank create/sign/send и PDF endpoint не
вызывались; последний требует POST и не входил в GET-only разрешение.
Ни один старый draft не проводился, не закреплялся за CRM и не получал новый
статус. Для read-only проверки backup/rollback не требовались.

## Риски и незавершённое

Проверка подтверждает форму Monobank executed statement и нескольких полей
Privat24 payment response на конкретных существующих записях. Она не заменяет
E2E нового draft с сохранённым creation context и не подтверждает реальную
получаемость Privat24 paid statement/PDF. Оба исторических примера содержат
изменённое назначение и корректно должны остаться вне auto-posting.

## Следующий шаг

Сохранить строгие проверки и выполнить согласованный новый E2E после release
gates; старые банковские/CRM операции автоматически не пересматривать.

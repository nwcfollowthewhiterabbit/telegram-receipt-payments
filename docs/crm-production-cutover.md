# Переключение CRM на рабочую базу

## Основание и границы

27.10.2026 пользователь сообщил о подтверждении заказчиком корректности
интеграции с тестовой базой и разрешил перенос на рабочую базу на том же
сервере. Это приёмка существующего маппинга. Правила дат, счетов, аналитик,
поиска получателя и статусов при переключении не меняются.

Read-only discovery подтвердил две доступные базы: `Terrasoft_test` и
`Terrasoft`. Рабочая цель — `Terrasoft`, таблица — `dbo.tbl_Cashflow`.
Исторические тестовые операции не копируются и не переигрываются. Новые
обработки после переключения создают операции в выбранной рабочей базе;
попытки с уже созданным платежом не используются для миграции истории.

## Инвариант и сценарий

Актор — прежний авторизованный пользователь бота; права Telegram и банков
не меняются. Действующий пользователь SQL должен иметь SELECT используемых
таблиц и INSERT операций/периодов. Новые роли или credentials не создаются.

```text
подтверждённая приёмка → проверенный source/image и backup → согласованное
переключение двух настроек CRM → проверка actual database до polling →
новая обычная обработка → банковский черновик и операция в рабочей CRM
```

Допустимые значения `TERRASOFT_DATABASE`: `Terrasoft_test` и `Terrasoft`.
По умолчанию остаётся тестовая база. До старта polling/банковского monitor и
в каждой транзакции записи должны совпасть:

1. Явно выбранная база в `TERRASOFT_DATABASE`.
2. База в SQLAlchemy URL `TERRASOFT_MSSQL_URL`.
3. Фактический результат `SELECT DB_NAME()` того же соединения.

URL должен быть прямым `mssql+pymssql`, с непустым сервером и без query
overrides. При несовпадении либо недоступности проверки запуск/запись
отклоняются. Ошибки проверки не раскрывают connection string. Dry-run и
отключённая CRM не требуют внешнего соединения. На успешном/ошибочном пути
созданный engine освобождается.

## Порядок установки и проверки

До изменения runtime отправляются implementation/observation commits,
подтверждаются remote SHA и successful CI с package-build/foundation-instance.
На сервер переносится exact CI image, проверяются checksum и revision.

Старый bot останавливается для согласованной копии PostgreSQL, конфигурации,
receipt-файлов, Compose override и прежнего image. Копия хранится отдельно
от runtime и проверяется восстановлением в изолированный PostgreSQL и новый
каталог файлов. Это локальный backup бота, не backup всей внешней CRM;
схема и существующие данные CRM не мигрируются. `testd` не используется.

В `.env` одновременно меняются только база URL и `TERRASOFT_DATABASE` на
`Terrasoft`. Сервер, credentials, остальные settings сохраняются. До старта
нового bot выполняется `verify_connection_target()` с новой конфигурацией.
Compose закрепляет новый immutable image; пересоздаётся только bot.

SQL smoke использует synthetic marker `HOWERP-E2E-…` и явную транзакцию:
реальный INSERT коннектора → чтение результата → обязательный ROLLBACK →
отдельным соединением отсутствие UUID во всех затронутых таблицах. Проверены
INSERT-триггеры Cashflow, CashflowRight, CashflowLog и DatabaseLog: внешних или
нетранзакционных действий нет. Для smoke не вызываются `sync_receipt()`
(он делает COMMIT), Telegram pipeline или банковские методы. DELETE для
очистки не используется. Видимость проверяется по созданным внутри
транзакции правам; интерфейс CRM проверяется на первой реальной операции.

После запуска проверяются exact image, polling, отсутствие перезапусков,
DB health, реальное имя CRM-базы и сохранение режимов банков. Отдельное
release evidence фиксирует фактический результат; этот документ сам по себе
не доказывает выполнение переключения.

## Откат и ограничения

При неуспешной проверке восстанавливаются сохранённые `.env` и Compose
override, запускается прежний bot/image. Нельзя откатывать только image:
старая версия разрешает исключительно тестовую CRM. Локальная БД и внешняя
CRM не восстанавливаются поверх новых пользовательских операций.

Уже записанные в рабочей CRM операции остаются в ней после отката. Сверка
интервала переключения выполняется отдельно, автоматического копирования
между базами или повторной отправки нет. Полная синхронизация статусов оплаты
не добавляется. Текущий маппинг описан в [самари бухгалтеру](crm-accountant-review.md).

Критерии проверки: startup отказ при неверной цели до банковской активности;
отказ записи при несовпадении actual DB до любых бизнес-запросов; успешный
test/prod target; dry-run без сети; сохранение маппинга; rollback smoke без
остаточных строк; healthy runtime на exact image.
